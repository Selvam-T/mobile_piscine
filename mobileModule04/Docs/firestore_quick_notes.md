# Firestore Quick Notes

Exercise 01 continues from Exercise 00. Exercise 00 already handles Firebase
initialization and Google/GitHub login. Exercise 01 adds diary notes stored in
Cloud Firestore.

## Firebase vs Firestore

Firebase is the full app platform: Authentication, Firestore, Storage,
Hosting, Cloud Functions, Analytics, and other services.

Cloud Firestore is the Firebase NoSQL document database used by this exercise.
Firebase Auth identifies the signed-in user. Firestore stores that user's diary
notes.

## Step 1 - Database Setup

Create the database in Firebase Console:

```text
Firebase Console > Build > Firestore Database > Create database
```

Use:

```text
Database ID: (default)
Mode: Production mode
Location: nearest suitable region
```

The app uses the default Firestore database. A custom database ID is not needed
for this exercise.

## Project Collection Structure

The project requirement shows a top-level collection named `notes`.

```text
notes
|
+-- auto-generated-document-id
|    uid: "FirebaseAuthUid"
|    usermail: "student@example.com"
|    date: Timestamp
|    icon: "satisfied"
|    title: "First entry"
|    text: "Today I learned Firestore."
|
+-- another-auto-generated-document-id
     uid: "AnotherFirebaseAuthUid"
     usermail: "other@example.com"
     date: Timestamp
     icon: "happy"
     title: "Second entry"
     text: "Another user's note."
```

One diary entry equals one Firestore document.

The document ID is auto-generated by Firestore when the application later calls
`.add(...)` on the `notes` collection. The app does not manually create document
IDs.

## Fields

Each note document should contain:

```text
uid       String       Firebase Auth user UID
usermail  String       Firebase Auth user email
date      Timestamp    note date
icon      String       feeling/icon value, for example "satisfied"
title     String       note title
text      String       note body
```

`uid` is not provided by the user. It comes from Firebase Authentication:

```dart
FirebaseAuth.instance.currentUser!.uid
```

Firestore does not auto-generate `uid`. Firestore only auto-generates the
document ID. The application writes the signed-in user's `uid` into each note.

## Security Rules

These rules were deployed for the project. They allow signed-in users to access
only documents where the document `uid` matches their Firebase Auth UID.

```js
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {
    match /notes/{noteId} {
      allow read: if request.auth != null
        && resource.data.uid == request.auth.uid;

      allow create: if request.auth != null
        && request.resource.data.uid == request.auth.uid
        && request.resource.data.keys().hasOnly([
          'uid',
          'usermail',
          'date',
          'icon',
          'title',
          'text'
        ])
        && request.resource.data.uid is string
        && request.resource.data.usermail is string
        && request.resource.data.date is timestamp
        && request.resource.data.icon is string
        && request.resource.data.title is string
        && request.resource.data.text is string;

      allow update: if request.auth != null
        && resource.data.uid == request.auth.uid
        && request.resource.data.uid == request.auth.uid;

      allow delete: if request.auth != null
        && resource.data.uid == request.auth.uid;
    }
  }
}
```

Important meanings:

```text
request.auth.uid           currently signed-in Firebase Auth user
resource.data.uid          uid on the existing Firestore document
request.resource.data.uid  uid on the document being created or updated
```

## Security Notes

Using `uid` is safer than relying only on email:

- Firebase Auth UID is stable and generated by Firebase Auth.
- Email addresses can change.
- The rules can compare document ownership directly with `request.auth.uid`.

Other production-oriented rules to consider later:

- Limit maximum length of `title` and `text`.
- Restrict accepted `icon` values to a known list.
- Prevent changing `date` after creation if the app requires that behavior.
- Add `createdAt` and `updatedAt` fields with server timestamps.
- Use Firebase App Check to reduce abuse from non-genuine clients.
- Test rules with the Firebase Emulator Suite.

## Step 2 - Data Model

The Flutter model was added here:

```text
mobileModule04/diary_app/lib/models/diary_entry.dart
```

`DiaryEntry` is application code. It represents one document from the Firestore
`notes` collection.

```dart
class DiaryEntry {
  const DiaryEntry({
    this.id,
    required this.uid,
    required this.usermail,
    required this.date,
    required this.icon,
    required this.title,
    required this.text,
  });

  final String? id;
  final String uid;
  final String usermail;
  final Timestamp date;
  final String icon;
  final String title;
  final String text;
}
```

The optional `id` stores the Firestore document ID after a document is read. It
is not written into the Firestore fields by `toMap()`.

## Model Conversion

Firestore stores document fields as map data. The model therefore has:

```text
toMap()    DiaryEntry -> Firestore field map
fromMap()  Firestore field map -> DiaryEntry
```

`toMap()` creates the exact fields expected by the security rules:

```dart
{
  'uid': uid,
  'usermail': usermail,
  'date': date,
  'icon': icon,
  'title': title,
  'text': text,
}
```

## Model Test

The model test was added here:

test command.

The test checks:

```text

Firestore map -> DiaryEntry object
```

It does not connect to Firebase and it does not create a document in the
Firestore `notes` collection. That database behavior belongs to the next
workflow step, the Firestore service layer.
